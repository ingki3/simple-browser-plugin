# 자동 로그인 설계안 (검토용 초안)

상태: 제안. 코드 변경 없음. 리뷰 대상은 이 문서의 보안 모델과 단계 구분이다.

## 1. 목표와 지킬 규칙

에이전트가 일을 하다 로그인 화면을 만나면, 사용자가 비밀번호를 직접 치지 않아도 로그인을 마치고 하던 일을 이어 간다.

지켜야 할 규칙(CLAUDE.md·사용자 결정):

- **비밀 값은 모델에 가지 않는다.** 아이디·비밀번호·일회용 코드는 모델 요청, 도구 결과·오류, 동작 기록(actionLog),
  디버그 로그(debugLog), chrome.storage 어디에도 남기지 않는다(#43 "사용자가 입력한 값은 보호").
- **키워드로 승인을 면제하지 않는다.** "로그인 버튼 같다", "login이라는 낱말" 같은 추론으로 채우기·제출을 자동 실행하지 않는다.
  예외는 구조(요소 종류, 프레임 출처)와 사용자의 명시적 선택으로만 만든다.
- **봇 탐지 우회를 하지 않는다.** 자동화를 막는 사이트, CAPTCHA, 패스키(WebAuthn), SMS 인증은 손 넘기기로 사용자에게 맡긴다.
- 확장에 비밀번호 저장소를 새로 만들지 않는다(암호화·백업·동기화를 다시 만드는 일이고, 확장 저장소는 평문이다).
  비밀번호는 이미 쓰고 있는 비밀번호 관리자에 둔다.

## 2. 조사한 방법

| 방법 | 확장에서 쓸 수 있나 | 판단 |
|---|---|---|
| Chrome 내장 비밀번호 관리자 | 확장 API가 없다. 채운 값도 사용자 동작 전에는 페이지 스크립트에 보이지 않는다 | 값을 꺼낼 수 없음. 손 넘기기와 함께 쓰는 1단계로만 |
| KeePassXC (오픈소스) | native messaging(`keepassxc-proxy`)과 공개된 KeePassXC-Browser 프로토콜(`associate`, `get-logins`, `get-totp`). 연결 승인·사이트별 접근 허락을 KeePassXC 창에서 사용자가 한다 | 2단계 1순위 |
| Bitwarden CLI (`bw`) | `bw serve`는 localhost REST라 확장 fetch에 Origin이 붙어 기본 출처 보호에 막힌다. 보호를 끄면 잠금 해제된 금고가 아무 웹페이지에도 열린다 | `bw serve` 직접 연결은 쓰지 않음. 쓰려면 native messaging 도우미가 `bw get`을 부르는 형태 |
| 1Password CLI (`op`) / Secure Agentic Autofill | `op`는 데스크톱 앱 연동·생체 인증으로 세션을 연다. Secure Agentic Autofill은 Browserbase 전용 조기 제공(엔터프라이즈) | `op`는 Bitwarden과 같은 도우미 형태로 3단계 후보. Agentic Autofill은 우리 구조(사용자 Chrome)에 맞지 않음 |
| browser-use `sensitive_data` | 모델에는 자리표시자만 보내고 실행할 때 실제 값으로 바꾼다. 화면 캡처로 새는 문제를 문서가 경고 | 설계 원칙만 가져옴(모델은 "로그인 정보 채우기"만 요청하고 값은 모름) |
| 쿠키·세션 유지 | 확장은 사용자의 실제 Chrome 프로필에서 돌아 이미 로그인된 상태를 그대로 쓴다 | 이미 됨. 자동 로그인은 세션이 끊긴 경우만 다룬다 |

## 3. 단계

### 1단계: 로그인 손 넘기기 (외부 연동 없음)

- content script가 구조로 로그인 양식을 알아본다: 보이는 `input[type=password]`가 있는 양식.
  낱말로 판단하지 않는다(버튼 글자·주소의 "login"을 보지 않는다).
- 모델이 그런 칸에 채우려 하거나(`fill_form_fields`가 비밀번호 칸을 대상으로 하면 지금도 승인 카드가 뜬다) 사용자에게 맡기기로 하면
  기존 손 넘기기 카드를 "로그인해 주세요"로 띄운다. 사용자는 Chrome 비밀번호 관리자·다른 관리자 확장의 자동 채우기를 쓰고 직접 제출한다.
- 끝남 판정: 사용자가 카드의 "완료"를 누르거나, 그 탭의 최상위 문서가 바뀐 뒤(`webNavigation` 커밋) 비밀번호 칸이 사라짐.
  모델에는 "로그인 완료/취소"만 알린다.

### 2단계: KeePassXC 연결 (선택 기능, 기본 꺼짐)

구성:

- manifest에 `nativeMessaging` 권한을 더한다. 설치 시 바로 쓰지 않으므로 `optional_permissions`로 두고 설정에서 켤 때 요청한다
  (가능한지 확인 필요: Chrome은 `nativeMessaging`을 선택 권한으로 허용한다).
- 사용자가 우리 확장 ID를 `allowed_origins`에 넣은 native messaging 호스트 manifest를 설치한다
  (이름 예: `com.simple_browser_helper.keepassxc`, `path`는 KeePassXC에 들어 있는 `keepassxc-proxy`).
  설정 화면에 OS별 설치 경로와 manifest 내용을 보여 주고 복사하게 한다(확장이 파일을 쓸 수는 없다).
- 처음 연결할 때 `associate`를 보내면 KeePassXC 창이 연결 승인과 이름을 묻는다. 받은 식별 키(id·공개 키)는 chrome.storage에 둔다
  (이것만으로는 금고를 열 수 없고, KeePassXC가 잠금 해제·접근 허락을 다시 확인한다). 세션 키는 메모리에만.

새 도구 `fill_login`(모델이 부른다):

- 인자: 대상 양식 id(`find_form_fields` 결과의 id)만. 사이트 주소, 아이디, 항목 이름은 받지 않는다.
- 백그라운드가 조회 주소를 **브라우저에서** 정한다: 대상 칸이 있는 프레임의 `documentId`·URL(`webNavigation.getAllFrames`).
  모델이 준 주소를 쓰지 않는다. https(또는 localhost)만 허용.
- `get-logins(url=그 프레임 URL)`. KeePassXC가 사이트별 접근 허락을 묻는다.
  여러 개면 사이드 패널에 아이디 목록으로 고르게 한다(아이디는 사용자에게만 보이고 모델에는 가지 않는다).
- 승인 카드: 항상 띄운다("example.com에 KeePassXC의 로그인 정보를 채웁니다"). 사용자가 카드에서 "이 사이트는 다시 묻지 않음"을 고르면
  출처별로 저장한다(명시적 선택). 이 면제는 채우기만이고, 제출 클릭은 기존 `decideApproval` 규칙을 그대로 따른다.
- content script에 값을 넘길 때 `documentId`로 고정해 그 사이 이동한 문서에는 넣지 않는다.
  채우는 칸은 구조로 고른다: 그 양식의 보이는 `type=password` 칸 하나와, 같은 양식에서 그 앞의 `autocomplete=username`
  또는 가장 가까운 text·email 칸. 대상 칸이 지금 그 프레임 문서에 붙어 있고 보이는지 다시 확인한다.
- 도구 결과는 "로그인 정보를 채웠습니다(항목 1개)"처럼 값이 없는 문장. 실패 이유도 값을 담지 않는다.
- 값은 지역 변수로만 다루고, 메시지 로그·디버그 로그·동작 기록 직렬화에서 빠지는지 테스트한다.
- 일회용 코드: KeePassXC 항목에 TOTP가 있으면 `get-totp`로 받아 `autocomplete=one-time-code` 칸(또는 사용자가 카드에서 고른 칸)에
  같은 방식으로 채운다. 2단계 안에서 뒤로 미룰 수 있다.

### 3단계(후보): 다른 관리자

같은 `fill_login` 계약 뒤에 공급자를 바꾼다. Bitwarden·1Password는 KeePassXC처럼 브라우저용 프로토콜을 열어 두지 않았으므로
작은 native messaging 도우미(우리가 배포하는 스크립트)가 `bw get item`/`op item get`을 부르는 형태가 된다.
도우미 배포·서명·업데이트 부담이 있어 1·2단계를 써 본 뒤 정한다.

## 4. 위협과 대응

| 위협 | 대응 |
|---|---|
| 페이지 글자의 프롬프트 주입으로 모델이 공격자 칸에 채우게 함 | 조회 주소·대상 프레임을 브라우저가 정하고, 그 프레임의 출처에 맞는 항목만 받는다. 다른 출처 iframe의 칸에는 넣지 않는다 |
| 같은 출처의 가짜 비밀번호 칸(사용자 글이 올라가는 사이트) | 보이는 `type=password` 칸만, 승인 카드에 출처·칸 위치를 보여 준다. 사이트별 면제는 사용자가 고른 경우만 |
| 채운 뒤 페이지가 다른 곳으로 이동 | `documentId` 고정. 이동했으면 넣지 않고 실패로 알린다 |
| 값이 모델·로그로 샘 | 결과 문장에 값 없음, 로그 직렬화 제외 테스트, 캡처 이미지는 모델에 안 보냄(이미 0.2.14) |
| 다른 로컬 프로그램이 우리 호스트 이름으로 위장 | native messaging 호스트는 사용자가 설치한 manifest의 경로로만 실행된다. 경로가 KeePassXC 설치 위치인지 설정 화면에서 보여 준다 |
| 자동 로그인을 봇 우회에 씀 | 하지 않는다. 사람처럼 보이게 하는 지연·궤적은 넣지 않고, 막는 사이트는 손 넘기기 |

## 5. 정할 것 (사용자)

1. 1단계(손 넘기기)만 먼저 할지, 2단계(KeePassXC)까지 할지.
2. 2단계 면제 범위: 채우기만 면제할지, 채운 뒤 제출 클릭까지 사이트별로 면제할지(제안: 채우기만).
3. TOTP를 2단계에 넣을지.
